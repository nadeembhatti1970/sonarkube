# sonarkube - production-grade SonarQube platform

Terraform and Kubernetes assets for the Code Quality Environment brief:
a security-optimised AWS VPC, a private EKS cluster, an isolated RDS PostgreSQL
instance and SonarQube deployed from the official Helm chart, plus the Day-2
"fixer" Job and a local Kind environment for the live demo.

Everything is split by responsibility into independent root modules that share
state through explicit `terraform_remote_state` contracts, so each layer can be
planned, reviewed and applied by a different owner.

---

## 1. Architecture

```
                          ┌──────────────────────────────────────────────┐
                          │  S3 remote state (versioned, SSE-KMS, lock)  │
                          └──────────────────────────────────────────────┘
                                            ▲
        ┌───────────────┬───────────────────┼───────────────────┬────────────────┐
        │               │                   │                   │                │
   core-infra/      core-infra/         core-infra/         core-infra/     core-infra/
 s3-remote-backend   core-vpc       core-secretsmanager     core-rds        core-eks
                                                                    │              │
                                                                    └──────┬───────┘
                                                                           ▼
                                                     ┌─────────────────────┴─────────────────────┐
                                                     ▼                                           ▼
                                    core-infra/core-external-secrets              core-infra/core-sonarqube
                                    (ESO + Pod Identity + ClusterSecretStore)    (ExternalSecrets + Helm)

AWS network (one region, 3 AZs)
┌────────────────────────────────────────────────────────────────────────────┐
│ VPC 10.20.0.0/16                                                            │
│                                                                            │
│  public  10.20.0.0/20    ALB / NAT gateways / IGW                           │
│  private 10.20.48.0/20   EKS managed nodes  ── NAT ──► internet             │
│  database 10.20.96.0/24  RDS PostgreSQL     ── no route to IGW or NAT ──    │
│                                                                            │
│  VPC flow logs (CMK) · interface endpoints (ECR, STS, Secrets Manager, …)  │
└────────────────────────────────────────────────────────────────────────────┘
```

Key properties:

* **Database isolation is structural, not just a security group.** The database
  subnets use a dedicated route table with no route to an internet or NAT
  gateway, and RDS has `publicly_accessible = false`.
* **Least-privilege connectivity.** PostgreSQL 5432 is reachable only from the
  `database-clients` security group, which is attached to the EKS managed node
  groups. No CIDR-based database access.
* **No long-lived credentials.** RDS and SonarQube passwords are generated by
  Terraform, stored in Secrets Manager under a customer managed key, and
  projected into Kubernetes. Kubeconfig uses `aws eks get-token`.
* **Private control plane.** The EKS API endpoint is private-only by default and
  every access grant goes through EKS access entries (API auth mode).

## 3. Backend and environment configuration

State configuration lives outside the code:

| File | Purpose |
| :--- | :--- |
| `<module>/dev.tfbackend` | S3 bucket, state key, region, SSE-KMS key alias, native S3 locking |
| `<module>/dev.tfvars` | Environment specific inputs (CIDRs, sizes, retention, feature flags) |

```bash
terraform -chdir=core-infra/core-vpc init -backend-config=dev.tfbackend
terraform -chdir=core-infra/core-vpc plan  -var-file=dev.tfvars
```

State keys follow `environments/<env>/<module>/terraform.tfstate`. Native S3
locking (`use_lockfile = true`) replaces the legacy DynamoDB table. Modules
require Terraform >= 1.11 for ephemeral resources and write-only arguments. The
bootstrap module deliberately uses local state; commit or archive its
`terraform.tfstate` in your own secure store.

## 4. Deployment order

```bash
# 0. Bootstrap the state bucket (local state, run once per account)
terraform -chdir=core-infra/s3-remote-backend init
terraform -chdir=core-infra/s3-remote-backend apply -var-file=dev.tfvars

# 1..6. Everything else consumes the state bucket
for module in core-vpc core-secretsmanager core-rds core-eks core-external-secrets core-sonarqube; do
  terraform -chdir=core-infra/$module init -backend-config=dev.tfbackend
  terraform -chdir=core-infra/$module plan  -var-file=dev.tfvars
  terraform -chdir=core-infra/$module apply -var-file=dev.tfvars
done
```

Why this order: VPC → secrets (containers + generated passwords) → RDS (writes
the JDBC endpoint into the secret) → EKS (writes the kubeconfig) →
External Secrets Operator (scoped to the exact secret ARNs, installs the
ClusterSecretStore) → SonarQube (installs ExternalSecrets and the chart).

> The EKS endpoint is private. `core-sonarqube` must run where the VPC is
> routable (VPN, SSM port-forward runner or a VPC-attached CI agent).
> Set `cluster_endpoint_public_access = true` and restrict
> `cluster_endpoint_public_access_cidrs` only if your operating model requires it.

## 5. Security decisions

| Area | Control |
| :--- | :--- |
| Network | Three tiers, isolated DB route table, no public DB, default SG emptied, default NACL restricted to the VPC CIDR |
| Egress | NAT gateways for private nodes, VPC interface/gateway endpoints so AWS API traffic never needs NAT |
| Audit | VPC flow logs to KMS-encrypted CloudWatch with 365 day retention, EKS control plane logs (api/audit/authenticator/controllerManager/scheduler), RDS PostgreSQL + upgrade log exports |
| Database | Multi-AZ, gp3 CMK encryption, 14 day backups, deletion protection, final snapshot, Performance Insights, Enhanced Monitoring, `rds.force_ssl=1`, IAM database authentication enabled |
| Cluster | Private endpoint, secrets envelope encryption with a dedicated CMK, IMDSv2 required, encrypted node volumes, no static cluster tokens |
| Credentials | Passwords generated as Terraform ephemeral resources and written with write-only arguments; Secrets Manager (CMK) is the source of truth; External Secrets Operator syncs them into Kubernetes via Pod Identity; Helm values never contain passwords; kubeconfig uses exec auth |
| Access | EKS access entries (admin/editor roles passed as data, not hardcoded IAM users), IRSA/pod identity for add-ons |
| Supply chain | Registry modules pinned to exact versions, providers pinned and locked in `.terraform.lock.hcl`, SonarQube chart pinned to `2026.5.1004` |
| Governance | `.checkov.yaml` suppressions each carry a written rationale; destructive plans are gated in `scripts/plan-guard.sh` |

Credential flow (no secret is ever persisted by Terraform):

```
ephemeral random_password (memory only)
  └── Secrets Manager secret version (write-only, KMS CMK)
        │
        ├── core-rds ──► RDS password_wo (no state)
        │
        └── core-external-secrets ── External Secrets Operator (Pod Identity)
                  │ reads at runtime, no Terraform involvement
                  ▼
        ExternalSecret sonarqube-db / sonarqube-admin
                  ├──► SonarQube Helm release (secrets by reference)
                  └──► sonarqube-db-fixer Job (files mounted from the Secret)
```

The only credential-related values in state are secret names/ARNs and the
integer revision counters that drive rotation. `scripts/check-secret-hygiene.sh`
enforces this statically.

## 6. SonarQube deployment

`core-infra/core-sonarqube` deploys `sonarqube/sonarqube` (Community Build) with:

* External PostgreSQL from RDS (`jdbcOverwrite` + password from the
  ESO-managed Kubernetes secret), `sslmode=require` when `force_ssl` is
  enabled;
* a gp3 `StorageClass` backed by the EBS CSI driver (Pod Identity, no static
  keys) and a 20 GiB PVC;
* admin password, monitoring passcode and server encryption key sourced from
  Secrets Manager and synced by External Secrets Operator;
* optional ALB Ingress (internal scheme, health check `/api/system/status`);
* `atomic`/`wait` installs with a 15 minute timeout for the DB migration.

Ingress is disabled by default because the AWS Load Balancer Controller is a
separate lifecycle. Install it, then set `ingress_enabled = true` and add the
ACM certificate annotation in `ingress_annotations`.

## 7. Part 2 - Day-2 database fixer

```bash
kubectl apply -f kubernetes/sonarqube-db-fixer/job.yaml
kubectl -n sonarqube wait --for=condition=complete job/sonarqube-db-fixer --timeout=120s
kubectl -n sonarqube logs job/sonarqube-db-fixer
```

The Job runs `UPDATE settings SET value='true' WHERE key='sonar.forceAuthentication';`
inside a transaction, verifies the row afterwards, and fails loudly if the row
does not exist (use the SonarQube API in that case). Credentials are mounted as
read-only files from the `sonarqube-db` Secret - no plaintext, no `kubectl exec`
into the app pod, and a NetworkPolicy limited to DNS and PostgreSQL.

See `kubernetes/sonarqube-db-fixer/README.md` for the full rationale and the
External Secrets Operator alternative.

## 8. Part 3 - Local live environment

```bash
# No arguments: reuse a running docker-desktop / minikube / kind cluster,
# otherwise create a Kind cluster
./scripts/local-up.sh

# Force a provider
CLUSTER_PROVIDER=docker-desktop ./scripts/local-up.sh
CLUSTER_PROVIDER=existing KUBE_CONTEXT=minikube ./scripts/local-up.sh

# first boot migrates the DB and builds the search index; wait for UP
kubectl --context <context> -n sonarqube exec sonarqube-sonarqube-0 --   curl -s localhost:9000/api/system/status

k9s --context <context> -n sonarqube   # :ns, :pods, l logs, s shell, e edit
kubectl --context <context> apply -f kubernetes/sonarqube-db-fixer/job.yaml
./scripts/local-down.sh                # removes the releases
CLUSTER_PROVIDER=kind DELETE_CLUSTER=1 ./scripts/local-down.sh  # also deletes Kind
```

The scripts use `--context` / `--kube-context` rather than switching your
current context, and rely on the cluster's default StorageClass (Kind:
`standard`, Docker Desktop: `hostpath`). Pin one with `STORAGE_CLASS=<name>` if
your cluster has no default.

Requirements: `kubectl`, `helm`, `openssl` and (for the demo) `k9s`. `kind` is
only needed when you want the script to create a Kind cluster; Docker Desktop
and minikube are detected automatically.
The local values mirror the production shape; only the host, TLS mode and
credential source differ.

## 9. Quality gates

```bash
./scripts/validate.sh                  # fmt, validate, secret hygiene, checkov, tests
./scripts/check-secret-hygiene.sh      # fails if any secret could reach state
./scripts/plan-guard.sh --self-test    # verify the destroy gate offline
./scripts/plan-guard.sh                # real plans (needs AWS credentials)
```

`validate.sh` output in this repository:

* `terraform fmt -check` clean
* `terraform validate` clean for all six modules
* `checkov` Terraform: 192 passed / 0 failed
* `checkov` Kubernetes + kustomize: 88 passed / 0 failed (1 documented skip:
  image digest, enforced by admission policy)
* `terraform test`: 114 assertions across 14 test files, all passing with mocked
  providers

`plan-guard.sh` exports each plan to JSON, scans it with Checkov's
`terraform_plan` framework and fails on any `delete` or `replace` action that is
not listed in the module's `testing/.checkov-allowlist.json`. All allowlists are
intentionally empty: there is no pre-approved destructive change in this
repository. The scanner is self-tested against fixtures in `scripts/testdata/`.

## 10. Trade-offs and next steps

* **RDS is given 90 minute create/update timeouts**; Multi-AZ and a final
  snapshot make teardown a deliberate, slow operation.
* **Automatic rotation** of the RDS master secret is wired
  (`enable_rds_master_rotation`) but disabled until a VPC-attached rotation
  Lambda is supplied; rotating the SonarQube admin password is a coordinated
  runbook because of `setAdminPassword`.
* **SonarQube uses the RDS master user today.** A dedicated least-privilege
  `sonar` role is the next step; it needs a migration hook (Job or Flyway) so
  the password can be rotated independently.
* **Secrets never enter Terraform state.** Passwords are ephemeral, writes use
  write-only arguments and the External Secrets Operator owns the Kubernetes
  projection. Rotation reaches the cluster within
  `external_secrets_refresh_interval` without a Terraform apply.
* **Single region.** State and logs are not replicated; recovery relies on
  versioning, non-current version retention and the CMK.
